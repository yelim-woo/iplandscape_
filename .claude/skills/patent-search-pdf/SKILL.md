# patent-search-pdf

특허 전문(PDF)을 입력받아 발명의 핵심 기술요소를 파악하고, 선행기술/유사특허 탐색용 검색식을 설계합니다.
patent-search와 **동일한 JSON 스키마 + 동일한 대시보드**를 사용합니다.

> ⚠️ **선행 의존성: 본 스킬은 단독으로 동작하지 않습니다.**
> 같은 프로젝트의 `.claude/skills/` 아래에 **patent-search 스킬이 함께 설치돼 있어야** 합니다.
> patent-search-pdf는 결과 저장 폴더와 웹 대시보드를 자체적으로 갖지 않고, 아래 경로의
> patent-search 자원을 **그대로 공유**하기 때문입니다.
>
> - 결과 저장: `${CLAUDE_PROJECT_DIR}/.claude/skills/patent-search/dashboard/public/stage1-results/`
> - 대시보드: `${CLAUDE_PROJECT_DIR}/.claude/skills/patent-search/dashboard`
>
> 폴더 이름은 정확히 `patent-search`여야 합니다(경로 하드코딩). patent-search 없이 본 스킬만
> 설치하면 저장 폴더·대시보드가 존재하지 않아 실행이 실패합니다.
> **두 스킬은 항상 세트로 설치하세요.** (git repo가 같은지/다른지는 무관 — 런타임은 설치된
> 디렉터리 구조만 참조합니다.)

## 실행 흐름

사용자가 PDF 파일 경로를 입력하면:

1. **PDF 읽기**: (먼저 `which pdftoppm` 로 poppler 설치 확인 → 없으면 설치 안내 후 중단) Read 도구로 특허 전문 텍스트 추출
2. **특허 구조 파싱**: 발명의 명칭, 요약, 청구항, IPC, 기술분야/해결과제/해결수단 식별
3. **검색식 설계**: 아래 지침에 따라 JSON 결과를 직접 생성
4. **파일 저장**: `${CLAUDE_PROJECT_DIR}/.claude/skills/patent-search/dashboard/public/stage1-results/YYYYMMDD_HHmm_특허요약.json` 으로 저장
5. **웹 실행**: 저장 즉시 Next.js 서버를 띄우고 브라우저 URL 안내

## Stage 0 — PDF 읽기 + 특허 구조 파싱

### ⚠️ 사전 점검: poppler(pdftoppm) 설치 확인 — PDF 읽기 전에 반드시 먼저 한다

Read 도구는 PDF 페이지를 이미지로 렌더링할 때 **`poppler`의 `pdftoppm`** 이 필요합니다. 이게 없으면 Read가 실패하고, **자동 설치를 시도하다 무한정 시간을 낭비**하게 됩니다(Homebrew 샌드박스 차단·X11 미러 404 등으로 실패 반복).

따라서 **PDF를 읽기 전에 먼저** poppler 설치 여부를 확인합니다:

```bash
which pdftoppm
```

- **경로가 나오면** → 바로 아래 "PDF 읽기"로 진행.
- **`pdftoppm not found` 이면** → **절대 자동 설치를 시도하지 말 것.** 아래 안내만 사용자에게 출력하고 **즉시 중단**한다. (brew/conda 설치를 Claude가 직접 돌리면 샌드박스·깨진 미러로 길게 헤맴)

  > 이 스킬은 PDF 렌더링에 `poppler`가 필요한데 설치돼 있지 않습니다.
  > **사용자 본인 터미널에서** 아래 중 하나를 실행한 뒤 다시 스킬을 실행해주세요:
  > ```bash
  > brew install poppler
  > # 또는 (anaconda 사용 시)
  > conda install -y -c conda-forge poppler
  > ```
  > 설치 후 `which pdftoppm` 으로 경로가 나오면 준비 완료입니다.

### PDF 읽기

**반드시 Read 도구를 사용합니다.** Python PDF 라이브러리(PyPDF2, pdfminer, pdfplumber, PyMuPDF 등)는 **절대 사용하지 않습니다.**

한국 특허 PDF는 CID 한글 폰트(BatangChe, GulimChe 등)를 사용하여 Python 라이브러리로 텍스트 추출 시 `???` 또는 깨진 문자가 출력됩니다. Read 도구는 PDF를 시각적으로(멀티모달) 인식하므로 이 문제가 발생하지 않습니다.

```
Read(file_path="<사용자가 준 경로>", pages="1-14")
```

- **한 번에 최대 20페이지**까지 읽을 수 있음
- 14페이지 이하 PDF: `pages="1-14"` 로 한 번에 읽기
- 15~20페이지 PDF: `pages="1-20"` 으로 한 번에 읽기
- 20페이지 초과 PDF: 먼저 `pages="1-20"` 읽고, 청구항이 뒤에 있으면 `pages="21-40"` 추가 읽기
- Read 도구로 읽히지 않는 경우(스캔 이미지 등)에만 사용자에게 텍스트 버전 요청

### ⚠️ 금지사항

아래 방법은 한글 특허 PDF에서 인코딩이 깨지므로 **절대 사용하지 않습니다**:
- `python` + `PyPDF2` / `pdfminer` / `pdfplumber` / `PyMuPDF(fitz)` 등 텍스트 추출
- PDF를 이미지로 변환 후 OCR (불필요한 복잡성)

### 파싱 대상

PDF에서 다음 정보를 추출/식별:

| 항목 | 설명 | 필수 |
|------|------|------|
| 발명의 명칭 | 한국어/영어 제목 | ✅ |
| 요약 | 기술 요약문 | ✅ |
| 독립 청구항 | 제1항 (장치/방법), 제7항 등 독립항 | ✅ |
| IPC/CPC 코드 | 특허에 부여된 분류 코드 | 있으면 활용 |
| 기술분야 | 발명이 속하는 기술분야 | 있으면 활용 |
| 해결과제 | 발명이 해결하려는 기술적 과제 | 있으면 활용 |
| 해결수단 | 과제를 해결하는 핵심 수단/구성 | 있으면 활용 |

## Stage 1 — 검색식 설계 지침

당신은 정부출연연구기관 연구담당자를 돕는 특허 정보 분석 전문가입니다.
**입력 특허의 핵심 발명 요소를 분석하여, 유사 특허 및 선행기술을 찾기 위한 검색식**을 설계합니다.
검색식은 **WIPS ON** (https://www.wipson.com/) 신택스로 작성합니다.

### 산출물 구조

patent-search와 **완전히 동일한 JSON 스키마**를 따릅니다:

```json
{
  "category": "기술분야 > 발명 명칭 요약",
  "globalKeywords": {
    "core": ["핵심키워드1", "핵심키워드2"],
    "exclude": ["제외키워드1"]
  },
  "taxonomy": [
    {
      "id": "A",
      "name": "대분류명",
      "scope": "범위 한 줄",
      "estimatedHits": 5000,
      "children": [
        {
          "id": "A.1",
          "name": "중분류명",
          "scope": "범위 한 줄",
          "estimatedHits": 2000,
          "children": [
            {
              "id": "A.1.1",
              "name": "소분류명",
              "scope": "범위 한 줄",
              "keywordGroups": [...],
              "ipcCodes": [...],
              "queries": { "basic": "...", "precise": "..." },
              "estimatedHits": 500
            }
          ]
        }
      ]
    }
  ],
  "unifiedQuery": { "basic": "...", "precise": "..." },
  "searchTips": ["팁1", "팁2"]
}
```

### ⚠️ patent-search와의 핵심 차이: taxonomy 설계 방식

| 구분 | patent-search (주제 기반) | patent-search-pdf (특허 기반) |
|------|---------------------------|-------------------------------|
| **목적** | 기술 전체 랜드스케이프 파악 | 입력 특허의 선행기술/유사기술 탐색 |
| **대분류 기준** | 기술 분야별 분류 (3~4개) | 청구항의 핵심 구성요소별 분류 (2~3개) |
| **소분류 수** | 15~25개 (넓게) | 8~15개 (좁고 정확하게) |
| **키워드 원천** | Claude 도메인 지식 | 특허 텍스트 직접 추출 + 동의어 확장 |
| **IPC 원천** | Claude 추정 | 입력 특허 IPC + 관련 IPC 확장 |
| **검색 전략** | 넓은 커버리지 | 정확한 매칭 우선 |

### taxonomy 설계 단계

#### Step 1: 독립 청구항 분해

독립 청구항(제1항 등)을 **핵심 구성요소**로 분해합니다.

예시 — "이동 로봇의 자율 주행 장치":
```
청구항 1: ... A부와 B부와 C부를 포함하는 이동 로봇에 있어서,
  상기 A부는 ... 하고,
  상기 B부는 ... 하며,
  상기 C부는 ... 하는 것을 특징으로 하는 ...
```

→ 대분류 후보:
- A: "A부" 관련 기술 (구성요소 1)
- B: "B부" 관련 기술 (구성요소 2)
- C: "A+B+C 결합" 관련 기술 (전체 시스템)

#### Step 2: 구성요소별 기술 트리 구축

각 핵심 구성요소를 대분류로 설정하고, 그 안에서:
- **중분류**: 구성요소의 세부 기능/방식별 분류
- **소분류**: 구체적 기술 방식/알고리즘/구조별 분류

#### Step 3: 키워드 추출 + 확장

1. **특허 텍스트에서 직접 추출**: 청구항/요약/상세설명에서 핵심 기술 용어 추출
2. **동의어/변형 확장**: 추출된 용어의 한국어 변형, 영어 대응어, 약자, 하위 개념 확장
3. **키워드 풍부함 유지**: 그룹당 8~15개 (patent-search와 동일한 풍부함 기준)

#### Step 4: IPC 활용

- 입력 특허에 IPC가 있으면 그것을 기반으로 관련 IPC 확장
- IPC가 없으면 기술 내용 기반으로 Claude가 추정

### 핵심 규칙

- **대분류 2~3개** (청구항 핵심 구성요소 기반)
- **중분류 2~3개** / **소분류 2~3개** (총 8~15 소분류)
- **대/중분류는 헤더만** (id, name, scope, estimatedHits, children)
- **검색식·키워드·IPC는 소분류에서만** 작성
- **IPC 코드는 서브클래스 단위(4자리)로만 작성** (예: `B25J`, `A61B`). 와일드카드(`*`)나 풀 코드(`B25J 9/16`)는 사용 금지
- 키워드 그룹: 단일 개념의 변형/동의어를 풍부하게 (그룹당 8~15개)
- 통합 검색식: 입력 특허 전체를 대표하는 키워드 8~15개
- 검색 누락이 노이즈보다 위험 → 동의어/변형 풍부하게

### WIPS ON 신택스

- `TIAB=(...)`: 제목+초록
- `IPC=(...)`: IPC 분류
- AND, OR, NOT (대문자)
- 한국어: 따옴표 없이, 영어 구문: 따옴표로 묶음, 와일드카드: `*`

### 키워드 그룹 type

- **include**: 검색에 포함 (OR 결합)
- **exclude**: 노이즈 제거 (NOT 결합), 노드당 0~1개

### ⚠️ 검색식 작성 원칙 (가장 중요!)

검색식의 두 가지 핵심 원칙은 **응집성**과 **풍부함**입니다. 둘 다 충족해야 합니다.

#### 🔴 절대 금지
1. **무차별 OR (응집성 위배)**: 서로 다른 카테고리의 키워드를 한 OR 묶음에 합치지 마세요
2. **키워드 부족 (풍부함 위배)**: 같은 개념의 변형이 풍부한데 2~3개만 쓰지 마세요
3. **중복 키워드**: 같은 단어를 두 번 넣지 마세요
4. **자식 OR 폭발**: 통합 검색식 = 모든 소분류 OR ❌ — 발명 대표어만 추리세요
5. **너무 일반적인 키워드**: "시스템", "통합", "기술", "응용", "방법" 등은 OR 묶음에 쓰지 마세요

#### 🟢 키워드를 풍부하게 만드는 5가지 차원
1. **한국어 변형**: 줄임말/풀이름/외래어 표기
2. **영어 풀네임**: `"reinforcement learning"`
3. **영어 약자**: DRL, LLM, PPO
4. **하위 개념/알고리즘**: policy gradient, actor-critic
5. **응용 형태**: "multimodal robot*", "language-conditioned*"

### 🟢 키워드 수 권장 범위
- 한 OR 그룹 (단일 개념): **8~15개**
- 소분류 검색식 전체 OR 키워드 합: **15~30개**
- 통합 검색식 OR 키워드 총합: **15~25개**

## 웹 대시보드 실행

patent-search의 대시보드를 **그대로 사용**합니다. 포트 충돌을 방지하기 위해 빈 포트를 자동으로 찾습니다.

```bash
cd "${CLAUDE_PROJECT_DIR}/.claude/skills/patent-search/dashboard"
if [ ! -d node_modules ]; then
  npm install --silent 2>/dev/null
fi
PORT=3000
while lsof -i :$PORT >/dev/null 2>&1 || netstat -an 2>/dev/null | grep -q ":$PORT "; do
  PORT=$((PORT + 1))
done
npx next dev --hostname 0.0.0.0 --port $PORT &
```

서버가 준비되면 **실제 사용된 포트 번호**를 포함하여 안내:

> 검색식 설계가 완료되었습니다.
> 브라우저에서 http://localhost:$PORT/stage1 을 열면 결과를 확인/편집할 수 있습니다.

## 종료

사용된 포트 번호로 종료한다:

```bash
npx kill-port $PORT
```

**주의**: `taskkill //F //IM node.exe` 절대 사용 금지. Claude Code가 함께 종료됩니다.

## 통합 검색식 작성 가이드

⚠️ **통합 검색식 ≠ 모든 소분류 키워드의 OR**

입력 특허 발명 전체를 대표하는 **8~15개 핵심 키워드**만 OR + 도메인 AND + IPC AND

→ 통합 검색식 한 번으로 입력 특허와 유사한 선행기술 윤곽 파악.

## 작성 규칙 (요약)
- 모든 검색식은 WIPS ON 신택스 그대로
- 모든 텍스트는 한국어 (영어 키워드는 그대로)
- estimatedHits: 정밀 검색식 기준 합리적 추정 (정수)
- IPC code 표시: `B25J 9/16` (공백 포함), 검색식 안에서는 `B25J9/16` (공백 없음)

## 검색 팁 작성 예시
- "입력 특허 출원일 기준 이전 선행기술에 집중하려면 AD=(19000101:YYYYMMDD) 추가"
- "입력 특허 출원인의 다른 출원 확인: PA=(...) 검색"
- "핵심 IPC 클래스 집중 탐색으로 노이즈 제거"
